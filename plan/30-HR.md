## 0. Conventions (apply to every WP)

- **Python standard library only** at runtime (`openpyxl` only inside `vendor.zip` for workbooks). No pip installs.
- New work lives in `hr_core/` beside the locked attendance engine; never touch `engine.py`,
  `calculation_engine.py`, `dashboard.html`, `PROJECT.json`, `hr_core/vendor/`, `eco_schemas/` (copied), or
  `hr_core/web/eco-ui/` (copied from GMES with `hr_core/eco_ui_pin.json`).
- Entities: add to `ENTITIES` in `hr_core/registry.py` (fields, codes, versioned records, soft delete / restore),
  business rules in a module file (like `scheduling.py`, `skills.py`, `discipline.py`), every access through
  `hr_core/service.py` (`require(user, perm)` + audit + `expected_ver` optimistic locking), routes in `hr_core/api.py`
  (`@route`), rights `hr.<area>.<action>` / `admin.*` in the auth profiles with templates, module status in
  `hr_core/modules.py` (`built` / `planned` / `design_only`) and editions.
- A change in data shape = a `DATA_VERSION` step in `hr_core/upgrade.py` (pre-update backup, put back, resume).
- Journal lines are signed; audit is append-only; secrets never in backups/logs/audit.
- Screens in `hr_core/web/app.js` built from the eco-ui kit; texts in `hr_core/web/i18n/en.json` and `ar.json`.
- `STATUS.md` inventory is **test-enforced** (`TEST_DOCS_CURRENT.py`: entities, routes, permissions, module statuses,
  tests, planted bugs) — update it in the same commit (that is not "hand-written docs"; it is part of done).
  `AGENT_HANDOFF.md`, `HISTORY.md`, `LESSONS.md`, design docs: at phase end (WP-D).
- Tests: extend the fitting `TEST_*.py` or add one (then register it in `CLAUDE.md` test list, `.github/workflows/ci.yml`
  and `STATUS.md`). Every new rule gets a planted bug in `migration/mutations.py` (tuple
  `(name, file, old, new, test)`). Run the full list from CLAUDE.md; then `git checkout -- sample/`.
- It must reach the installed program: `tools/build_windows.py` includes new modules; installer job green.

## WP-H1 · HR inbox, crew requirements, staffing gap, work centres — size M

1. **Machine keys + inbox:** table in `auth.db` `machine_key(id, name, hash, scopes, active, created_at)`; admin route
   to create (printed once) and screen; `POST /eco/v1/inbox` (header `x-eco-key`, scope `eco.inbox.write`, same
   result vocabulary as GMES: applied / unchanged / stale / duplicate / rejected; dedupe `(source, id)` in
   `data/eco_inbox.db`); rejects foreign company and non-accepted types. Accepted types:
   `mes.crew_requirement.v1`, `mes.labor_day.v1`.
2. **Work centres:** new entity `work_center(code = the GMES line code, name, org_unit_id, active)` and optional
   `work_center_code` on `shift_assignment` and `roster_override` (which line the person works on for that
   assignment/day). Publish it: **additive** field `line?: zCode` in `eco.schedule_day.v1` (WP-C1 adds it in GMES;
   copy schema) — the schedule day carries the line when known.
3. **Crew requirement mirror** (`crew_requirement(line_code, shift_code, work_date, headcount, skills JSON, version)`)
   and the **staffing gap** service: for each line × shift × day: required headcount and per-skill counts vs people
   scheduled there (`schedule` resolution + `work_center_code`) who hold a **valid** qualification at the level on that
   day; gap = required − covered (per skill and total); `GET /api/staffing/gap?from=&to=&line=`.
4. Screen "Staffing plan" (line × day grid for a shift: required / covered / gap, click → who is scheduled, who is
   qualified but free, who is on leave) with actions: assign (temporary assignment), request overtime (WP-H3), raise
   a hiring requisition (WP-H2).
5. Tests: inbox auth and dedupe; gap arithmetic with expired / not-yet-valid qualifications; overnight shift date rule;
   planted bugs: expired qualification counted; line ignored.

## WP-H2 · Headcount plan and recruitment (requisition → hire → onboarding) — size M–L

Entities (registry) and rules:

| Entity | Fields | Rules |
|---|---|---|
| `headcount_plan` | code, org_unit_id or work_center_code, job_id, period (YYYY-MM), planned_fte, source `manual`\|`crew_requirement`, note | "Propose from crew requirements" computes the average required headcount per line × month ÷ shifts coverage factor (1.0 + relief % setting, default 8 %) |
| `requisition` | code REQ-nnnn, job_id, position_id?, work_center_code?, count, employment_type `regular`\|`fixed_term`\|`agency`\|`intern`, reason `crew_gap`\|`replacement`\|`growth`\|`seasonal`, needed_by, contract_months?, agency_code?, status `draft`→`approved`→`open`→`filled`\|`cancelled`, approved_by | approval is a separate right `hr.recruitment.approve` (SoD with `hr.recruitment.write`); count ≤ plan gap unless an override note |
| `agency` | code, name, contact (company, not person), fee_percent, active | for agency temps |
| `candidate` | code CAN-nnnn, requisition_code, display_name, source `agency`\|`referral`\|`walk_in`\|`online`, stage `applied`→`screened`→`interviewed`→`offered`→`hired`\|`rejected`\|`withdrawn`, stage dates, notes | personal data stays in HR; never published |
| `onboarding_task` | employee_code, kind `medical`\|`badge`\|`ppe`\|`esd_training`\|`station_training`\|`contract_signed`, due, done_on | a new hire is **not schedulable on a production line** until `medical`, `ppe`, `esd_training` are done (schedule save refuses `hr.onboarding.incomplete`) |

**Hire** command (`POST /api/recruitment/candidates/<code>/hire {hire_date, position, work_center, employment_type,
contract_end?, agency?}`): creates the employee (next code, `worker_type`, `hire_date`, contract end for fixed-term,
agency link), fills the requisition count, creates the onboarding checklist, audits. Published as `eco.employee.v1`
(no personal data — unchanged contract). Contract end reached → employee status becomes `Terminated` on that date
(daily job) with reason `contract_end`.

Screens: Headcount plan, Requisitions (approve), Candidates pipeline (kanban by stage), Onboarding.
Tests: SoD, over-plan refusal, hire creates employee + checklist, not schedulable before onboarding, contract end.
Planted bugs: approval by the same person; schedulable without ESD.

## WP-H3 · Overtime under Labour Law 14/2025 — size M

Research: `complete-company/research/TV_INDUSTRY_REFERENCE.md` §6 (overtime ≥ +35 % day, ≥ +70 % night; rest-day
work = substitute day + premium; daily cap incl. overtime **must be verified against the law text — keep it a
setting, default 10 h, with the source note**).

- Entity `overtime_request` (code, employee_code, work_date, planned_minutes, kind `day`\|`night`\|`rest_day`\|
  `holiday`, reason, requested_by, status `requested`→`approved`\|`rejected`, approved_by) — separate right to approve.
- Settings `overtime_policy` (premium_day_bp 3500, premium_night_bp 7000, rest_day_premium_bp 10000,
  holiday_premium_bp 10000 (verify), night window 19:00–07:00 (verify), max_daily_minutes_incl_ot 600,
  max_weekly_ot_minutes, max_monthly_ot_minutes, night_allowance_bp 1500 (company policy), substitute_day_for_rest_day
  true).
- **Actuals**: from attendance (`worked_minutes` beyond the scheduled paid minutes) confirmed against GMES
  `mes.labor_day.v1` evidence (report differences); only approved overtime is paid; unapproved actual overtime shows as
  an exception.
- Output service `overtime_for_period(period)` → per employee: minutes by kind, premiums in basis points, substitute
  days owed — the payroll input (WP-H6).
- Screens: Overtime requests (bulk request for a line × shift from the staffing plan), Overtime actuals vs approved.
- Tests: caps refuse; night classification of a C shift; rest-day substitute day; unapproved actual flagged.
